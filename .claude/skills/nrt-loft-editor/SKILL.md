# NRT LOFT 記事添削

NRT LOFT の記事草稿を受け取り、レギュレーションに照らして指摘を返す。

## このスキルの最重要事項

**失敗・うまくいかなかった話・家族に断られた話を削る提案をしてはいけない。**

一般的な記事の基準ではこれらは弱点に見える。しかし NRT LOFT の差別化はまさにそこにある。添削を通すたびに記事が普通のAI紹介記事に近づくのを防ぐことが、このスキルの存在理由。

## 前提

**メディアの定義**
成田にある拠点の名前であり、そこで行われている活動の名前。AIを使って「自分の困りごとを解決する小さな仕組み」をつくり、その過程を記事とYouTubeで発信する。運営はNebulab合同会社。発信者はKoki（エンジニア、成田、小学生と中学生の子どもがいる）。

**読者**
非エンジニアの生活者。プログラミングを学びたい人ではない。アプリ開発者になりたい人でもない。副業で稼ぎたい人でもない。「家の困りごとが片づいてほしい」人。

**発信者の役割**
エンジニアが一般の人にAIでのものづくりを翻訳する。教える立場ではなく、訳す立場。

**伝えたいこと**
「欲しいものがなければ、自分で作ってしまう」という新しいAIの使い方そのもの。

**差別化の3点**（これ以外に差別化はない）
1. 成田の自分の家という具体性
2. 失敗を出すこと
3. 家族に渡して断られる過程

題材では差別化しない。生活系のAI活用事例は既に多数存在する。

## 手順

1. 記事全文を読む
2. 下記「絶対条件」に照らす。1つでも違反があれば判定は差し戻し
3. カテゴリを判定し、現在の分類と一致するか確認
4. 該当カテゴリの構成チェックを行う
5. `references/existing-claims.md` を読み、既存記事の主張と衝突していないか確認
6. `references/publication-order.md` を読み、先に出すべき記事があるか確認
7. 出力形式に従って返す

---

## 絶対条件（1つでも違反したら差し戻し）

### 1. 技術から入らない

記事の冒頭は困りごとから始まる。技術名・ツール名から始まる記事は差し戻し。

- NG: 「Claude CodeでNext.jsアプリを作ってみた」
- NG: 「AIを使えば◯◯ができます」
- OK: 「冷蔵庫の中身が分からなくなるので、自分専用の管理ツールを作った」

### 2. 「アプリ開発」と言わない

非エンジニア読者にハードルを作る語を使わない。

**使わない語**: アプリ開発 / アプリを作る / 開発する / エンジニアになる / プログラミングを学ぶ / デプロイ / リリース / App Store公開

**代わりに使う語**: 小さな仕組み / 自分専用ツール / 作った / 出せるようにした

### 3. 公開・サービス化を目的にしない

「まず自分ひとりが使えればいい」から始める。記事の結論が「これを公開しました」「サービス化を目指します」になっていたら差し戻し。

例外: JOURNEY で拠点（レンタルスペース等）の話を書く場合。ただし時期・料金・利用方法は書かない。

### 4. 「AIで稼ぐ」を主軸にしない

副業 / 収益化 / 稼ぐ / 月◯万円 / 案件獲得。これらを主題にした記事は差し戻し。

### 5. 効果を断言しない

書けるのは事実だけ。量、期間、実際に出た発言。

- NG: 「成績が上がりました」「生産性が3倍になりました」「思考力が育ちます」
- OK: 「2人とも実際にやりました。◯ページ分、◯日間続きました」
- OK: 「苦手な分野を本人が言葉にできるようになりました」

教育効果・健康効果・学習効果はエビデンスが弱い領域。断言したら差し戻し。

### 6. 一次情報で確認する

料金、プラン内容、利用規約、年齢制限、サービスの仕様を書く場合、公式の一次情報で確認し、**確認日を記事に明記する。** 二次情報（他人のブログ、まとめ記事）を根拠にしていたら差し戻し。

添削側では正しさを検証できない。**確認日の記載があるかだけをチェックし、実際の確認は書き手の工程として残す。**

### 7. 個人情報

記事内の画像・本文に以下が含まれていたら差し戻し。

氏名 / 学校名・園名 / クラス・学年 / 住所 / 電話番号 / 保険証の記号番号 / 口座番号・カード番号 / 他人の住所・氏名 / 病院名

**写真は全部写る。** プリントの端に印刷された情報も渡っている。伏せ漏れをチェックする。

### 8. 家族の扱い

- 子どもの顔・声・名前・学年は出さない
- 子どもの発言を載せる場合は要約。直接引用は避ける
- 妻の発言・反応を載せる場合、本人の了解を取ったことを確認
- 数年後に本人が読んで嫌がる内容になっていないか
- 「使えなかった」を家族の能力の話として書いていないか。**責任は渡した側にある**

## カテゴリ判定

記事の入口で決める。使った道具では決めない。

| 入口 | カテゴリ |
|---|---|
| 困りごと → 作った → 生活が変わった | **BUILD** |
| 作って分かったこと、失敗、AIとの付き合い方 | **LEARN** |
| 道具、費用、環境、判断の材料 | **TOOLKIT** |
| NRT LOFT自身の活動、拠点、数字、裏側 | **JOURNEY** |

判定の1問: **記事の1行目が困りごとから始まるならBUILD、道具から始まるならTOOLKIT。**

例:
- 「お風呂のフックが壊れて、同じ形が売っていないので作った」→ BUILD
- 「3Dプリンターを導入した。何を基準に選んだか」→ TOOLKIT
- 「レーザーカッターで最初に詰まったこと」→ LEARN
- 「拠点の共有部を工事した」→ JOURNEY

DIY（リノベーション、キャンプ用品、3Dプリンター、レーザーカッター）は独立カテゴリを作らない。拠点の話は JOURNEY。それ以外は上記の判定に従う。DIY は記事の中に繰り返し出てくる比喩として使う（シリーズの通し軸）。

**カテゴリは企画段階で決まっている。** 現在の分類と判定が違う場合は指摘するが、変更を強く勧めない。指摘のみ。

## BUILD の構成

以下の順序を守る。

1. 日常の困りごと（具体的なエピソード1つ）
2. 「こんな仕組みがあったらいい」
3. 何を作ることにしたか。**捨てたものも書く**
4. AIに何を話したか（依頼文の掲載）
5. 作った記録。**詰まったところを必ず1つ以上**
6. 動かしてみる（Before/After）
7. 生活がどう変わったか。**変わらなかったことも書く**
8. 実はこんな簡単な仕組みで動いている
9. 同じことをやるなら

### チェック項目

- [ ] 冒頭に具体的なエピソードがあるか（一般論から始まっていないか）
- [ ] 「捨てたもの」の節があるか
- [ ] 詰まったところ・失敗が1つ以上書かれているか
- [ ] 「変わらなかったこと」「うまくいかなかったこと」があるか
- [ ] 「実はこれだけの仕組み」で読者が驚く設計になっているか
- [ ] 最後に読者への手渡しがあるか（最小構成でいい、公開しなくていい）
- [ ] 数字が1つ以上入っているか（枚数、分数、回数、日数）

### LEARN / TOOLKIT / JOURNEY

BUILD ほど構成は固定しない。ただし以下は共通。

- 失敗・限界・分からなかったことを書く
- 一般論で終わらず、自分の実測・実体験に落とす
- TOOLKIT で料金・道具を扱う場合、冒頭で「◯年◯月時点の自分の環境の話。一般論ではない」と宣言する

## タイトル

### 基本型

「○○が面倒なので、自分専用の○○を作った」

### 別型

- 「誰も作ってくれないので、自分で作ることにした」
- 「毎日○分取られていた○○を、AIでなくした」
- 「自分のためだけの○○を作る」
- 「○○を試して、全部やめた。だから自分で作った」

### 必須

- 技術名を入れない
- 困りごとを入れる
- BUILD なら「作った」を入れる

### 検索を狙う場合

- 記事タイトル: 検索型（困りごとのキーワード）
- YouTubeタイトル: ストーリー型（面白み優先）

同じ内容で使い分ける。矛盾ではなく、決めてある役割分担。

## 触ってはいけない領域

法人メディアが数日単位で更新しており、網羅性と更新頻度で勝てない。**見出しにこれらを置かない。**

- 「Claude Codeとは」
- 「完全入門」「使い方」
- 料金プランの網羅的な比較表
- Cowork / Codex / Claude Code の機能比較表
- 「用途に応じて選びましょう」で終わる結論

**書いてよい場合**: 自分の実額・実体験としてなら書ける。冒頭で「◯年◯月時点の自分の環境の話。一般論ではない」と宣言し、そのうえで断言する。

### 検索の競合状況

- プリント管理系: 既存アプリ（プリゼロ、ポスリー、まなびの手帳）とベネッセ・VERYが上位。正面衝突を避け「アプリを試して全部やめた」側から入る
- 料金系: 法人メディアが占拠。家計の記事にする
- 入門系: 33万再生の動画がある。作らない

## 文体

### 基本

- 丁寧体（です・ます）
- 見出しも丁寧体に揃える
- 読者の呼び方は「方」（「人」は硬い）

### 冒頭で立場を宣言する

私的な記事なら冒頭で宣言する。宣言したら、あとは断言で書く。

- OK: 冒頭に「成田の一軒家で、月に数個の小さな仕組みを作っている個人の記録です。一般論ではありません」→ 本文は「$20では足りない」と言い切る
- NG: 毎段落に「私の場合は」「個人的には」を付ける（自信がない記事に見える）

### 避ける表現

「ぜひご覧ください」/ 「いかがでしたか」/ 「〜ではないでしょうか」（断言を避ける癖）/ 「魔法のような」「革命的な」/ 「元が取れた」（元を取ることが目的でないなら）

## 素材

### Before素材は作り終わってからでは撮れない

以下を撮る前に作り始めていたら指摘する。

- 困っていた状態（紙の山、探している様子、余ったドリル）
- 実物（処分される前）

### 再現撮影をした場合

記事内でそう書く。隠して使うと信頼を失う。差別化が「失敗を出すこと」なら、素材の再現も同じ基準で扱う。

### 撮影素材の伏せ漏れ

学校名・氏名・クラスが写るものは、ダミーを用意するか黒塗り。動画で一瞬映る場合も同じ。

## SNS投稿の追加基準

記事より厳しくする。**SNSは拡散し、一度出た画像は取り消せない。**

- 記事では伏せて載せる程度でよくても、SNSでは出さない判断がある
- リールで一瞬映る場合、伏せ漏れに気づけない。事前に確認する
- 子どもが写るものは出さない

### 告知投稿の型

- 困りごとから始める
- タイトルを言わない
- 「ぜひご覧ください」を書かない
- 実物の写真を1枚付ける

### X で投稿しないもの

AI最新情報の速報 / 他のAIツールの紹介 / 「◯◯する方法」系のスレッド / 数字の報告（フォロワー、再生数） / 政治・社会の話

## 出力形式

```
## 判定
[差し戻し / 修正が必要 / 公開可]

## 絶対条件の違反
（項目番号と、該当箇所を引用）

## カテゴリ
[BUILD / LEARN / TOOLKIT / JOURNEY]
（記事の入口から判定。現在の分類と違う場合は指摘のみ）

## 構成のチェック
（チェック項目のうち欠けているもの）

## 記事間の整合
（既存の主張と衝突していないか。衝突する場合、認めて書く方向を提案）

## 表現の指摘
（該当箇所と修正案）

## 一次情報の確認が必要な箇所
（料金・規約・仕様が書かれている箇所と、確認日の記載があるか）

## 個人情報の確認が必要な箇所
（画像・本文の該当箇所）

## 公開順
（先に出すべき記事があるか）

## 良い点
（差別化の3点に該当する部分。ここは削らせない）
```

**「良い点」は必ず書く。** 失敗・うまくいかなかった話・家族に断られた話がある場合、それを良い点として明示する。**削る提案は絶対にしない。**
