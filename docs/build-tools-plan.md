# BUILD の 3 本を「本当に作る」計画（2026-09-20 起草）

**きっかけ（運営者）**: BUILD の記事 3 本（買い物リスト／冷蔵庫の在庫／学校のプリント）は、まだ実物が無い。
これから実際に作り、作る過程をキャプチャで撮って記事をリライトする。**投稿日時（`date`）はそのまま。`updated` だけ動かす。**

この文書は 3 つのツールの設計。実装は 1 本ずつ、設計 → 実装 → 家族に渡す → 記事のリライト の順で回す。
`docs/HANDOFF.md` 2 節の思想（自分ひとりが使えればいい、実装方式にこだわらない、失敗と家族の反応を出す、紙で出す・学年差の軸）に従う。

## 0. 全体の決め方

| やらないこと | ログイン、公開、複数家族、プッシュ通知、ネイティブアプリ、在庫と買い物リストの連携、価格の記録、カテゴリ分け | 記事に「入れない機能」として既に書いてあるものは守る |

技術の形: Next.js 16（App Router）、TypeScript、Tailwind 4、Neon Postgres（postgres.js をサーバーから）、`@google/genai`（Gemini）、Google Calendar API（プリントだけ）。スマホのブラウザで使う前提（ホーム画面に追加できるように manifest を置く）。

## 1. 買い物リスト `/list`（記事: shopping-list、2026-07-30）

記事の仕様「家族の誰でも足せる／スーパーの近くに来たら通知／買ったものはその場で消える」をそのまま実装する。

### 画面（1 枚）
- 上に入力欄 1 つ（「牛乳」と打って Enter）。下に未購入の一覧。
- 行をタップで「買った」→ その場で消える（取り消しは 5 秒だけ「戻す」を出す）。
- 一覧は 3 秒ごとに再取得（家族が同時に見る。リアルタイム購読は入れない）。
- 誰が足したかは出さない（入れない機能）。並びは追加順。

### データ
```
list_items (id, name text, added_at timestamptz, bought_at timestamptz null)
```
「消える」は `bought_at` を入れるだけ（消さない。後で「先月よく買ったもの」を出せる余地。画面には出さない）。

### 「店に着いたら開く」
- iOS ショートカット → オートメーション → 「到着」→ 店を指定 → 「URL を開く」に `/list` の URL。**家族の各スマホで 1 回だけ設定**。設定手順の画面をキャプチャして記事に載せる。
- 記事の「通知が出る」は、ショートカットのオートメーションが出す通知（「実行しますか」）で成立する。実物に合わせて文言を直す。

### 失敗の記録候補（記事用）
- 最初は Web プッシュを試して iOS で届かず、ショートカットに逃げた（実際に試して失敗したら書く。試さずには書かない）。
- 中学生が「LINE でいい」と言うかどうか。

## 2. 冷蔵庫の在庫 `/fridge`（記事: fridge-inventory、2026-08-14）

記事の仕様「レシートを撮ると品名が入る／期限は自動で推定／期限が近い順／期限が近い 3 つで献立を出す／使い切ったらタップ 1 回で消す」。

### 画面
- `/fridge`: 期限が近い順の一覧（品名・推定期限・「あと n 日」）。行をタップで「使い切った」。上に「レシートを撮る」ボタン（`<input type="file" capture>`）。
- `/fridge/recipe`: 期限が近い 3 つを固定表示 → 「これで作れるもの」を 3 案（料理名と 3 行の作り方）。
- `/fridge/print`: A4 1 枚。品名と期限だけの表。

### データ
```
fridge_items (id, name text, category text, expires_on date, source text check in ('receipt','manual'),
              added_on date, used_at timestamptz null, receipt_id uuid null)
fridge_receipts (id, taken_at timestamptz, image_path text, raw_text text)
```

### AI（実物の指示文を記事に載せる）
1. レシート → 品名の一覧（JSON）。指示: 「食品だけ。単位・価格は要らない。分からない略称は推測せず `?` を付ける」。
2. 品名 → 期限の推定。**まず固定の表**（`category → 日数`: 葉物 4 日、豆腐 5 日、牛乳 7 日、卵 14 日、肉 2 日、冷凍 30 日…）で当て、表に無いものだけ AI に「カテゴリを 1 語で」と聞く。**期限そのものを AI に決めさせない**（それらしい嘘の日付を防ぐ。プリントの記事の学びと同じ）。
3. 献立: 「次の 3 つを使う、平日の夜に 20 分で作れる料理を 3 つ。それぞれ材料と手順 3 行」。

### 入れない機能
数量、単位、価格、カテゴリの手動選択、賞味期限の写真読み取り（レシートに無い）。

### 失敗の記録候補
- レシートの略称（「ﾄｸﾆｭｳ 1000」）が読めない → 「?」を付けて人が直す運用に落ち着く。
- 推定期限が外れて怒られる（実際の家族の反応）。

## 3. 学校のプリント `/prints`（記事: school-print-to-calendar、2026-08-28）

記事の仕様「写真 → 文字 → いつ・何を・誰が → カレンダー → 持ち物は前日の夜に通知」。記事に載っている指示文（撮影日を渡す、「要確認」と書かせる）を**そのまま実装**する。

### 画面
- `/prints`: 「撮る」ボタン → 結果の確認画面（抽出した項目の表: 種類（提出物／持ち物／行事）、日付、内容、誰の（小学生／中学生）、`要確認` の印）。**人が確認して「カレンダーに入れる」を押すまで登録しない**（8 割自動・2 割手直し、を画面の形にする）。
- `/prints/list`: 登録済みの予定（今週・来週）。持ち物は前日 20:00 の通知付きで登録されたことが分かる印。
- `/prints/print`: A4 1 枚。今週と来週の予定と持ち物（冷蔵庫に貼る用）。

### データ
```
print_scans (id, taken_on date, child text check in ('elementary','junior_high'), image_path text, raw_text text, model_output jsonb)
print_items (id, scan_id, kind text check in ('submission','belongings','event'), on_date date null, needs_check boolean,
             title text, child text, calendar_event_id text null, created_at)
```

### AI
- 画像 → 文字と項目を 1 回で（画像入力）。指示文は記事のものを使い、「今日は YYYY 年 M 月 D 日です」を撮影日で埋める。出力は JSON（`kind`, `date | null`, `title`, `needs_check`, `reason`）。
- `needs_check=true` の行は日付を空にして、画面で人が入れる。

### カレンダー
- Google カレンダー API。**家族の Google アカウント 1 つ**で OAuth（refresh token をサーバーの環境変数に。BizRelay と同じ作法。scope は `calendar.events`）。
- 子どもごとにカレンダーを分ける（「小学生」「中学生」の 2 つ。無ければ最初に作る）。
- 持ち物は前日 20:00 の popup 通知を付けて登録。提出物は当日 07:00。行事は終日。

### 入れない機能
持ち物と家にあるものの照合（記事の「まだできていないこと」のまま残す。正直に）。学校からのメール／アプリの取り込み。

### 失敗の記録候補
- 「来週木曜」が撮影日なしでずれる実例（わざと再現して記事に載せる）。
- 中学生のプリントは小学生より情報が少なく、抽出が空になる。

## 4. 作る順序と、過程の撮り方

順序: **買い物リスト → 冷蔵庫 → プリント**（公開日の順。小さい順でもある）。

各ツールで残すもの（記事の素材）:
1. 最初の相談の文面（Claude Code に投げた最初のプロンプト。そのまま `docs/log/<tool>/01-first-prompt.md` に保存）
2. 途中で詰まった箇所と、そのときのやり取り（同じフォルダに番号順で）
3. 画面のキャプチャ（iPhone 幅 390px、ライトモード。ヘッドレス Chrome の 2 倍解像度で撮る。`public/images/<記事>/` に webp で）
4. 家族に渡したときの反応（運営者がメモ。1 行でよい）
5. 「作ってみたら要らなかった機能」と「後から足した機能」の一覧

記事のリライトの決まり: `date` は変えない。`updated` を公開日に。写真素材（Unsplash）は残してよいが、**実物のキャプチャが入る節では実物を優先**。「一般には公開していません」の一文は、実際に公開しない限り残す。
